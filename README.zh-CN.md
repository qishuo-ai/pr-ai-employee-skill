# PR AI Employee Skill｜公关 AI 员工技能

> 让 AI 不只是会写稿，而是像一名真正的公关员工一样：理解客户、做策略、管项目、控风险、交付结果。

**作者：Qishuo（骐铄） · 与 Yubai（予白）共同构建**

---

## 这是什么？

`PR AI Employee Skill` 是一套面向 **公关、品牌传播、汽车营销、Agency 客户服务与项目管理** 的开源 AI Skill。

它不是一个“万能公关 Prompt”，也不是一个只负责生成新闻稿、社媒文案的内容工具。

它真正解决的是：

- 客户说一句话，AI 能不能判断客户真正想解决什么？
- 这件事是普通需求，还是已经构成了交付、价格、范围或责任承诺？
- 一个传播方案到底有没有策略，还是只是动作堆砌？
- 汽车参数、车型配置、上市版本等事实能不能被准确核验？
- 客户突然加需求时，是直接答应，还是应该先走变更和报价？
- 危机发生后，AI 能不能知道什么时候必须停下来等真人？
- AI 生成的内容有没有独立审核机制，而不是自己写、自己批？

核心目标是：

> **把成熟公关从业者的职业判断、项目方法和风险意识，转化成 AI 可以执行的工作规则。**

# 核心能力

## 1. 公关策略 PR Strategy

把 Brief 从“客户要什么动作”重新还原为“客户真正需要解决什么业务问题”。

默认策略链路：

```text
事实 / 信号
→ 行业或用户变化
→ 核心矛盾
→ 对品牌的影响
→ 可占领机会
→ 策略选择
→ 传播机制
→ 执行动作
→ KPI / 验收
```

避免典型 AI 式策略：

- 年轻化
- 高端化
- 破圈
- 全域
- 生态
- 品效合一

这些词可以出现，但必须说明 **为什么、凭什么、如何成立、最终怎么执行和验收**。

---

## 2. 客户沟通 Client Service

AI 不应该把所有客户消息都当成“帮我润色一句回复”。

它必须先判断：

- 客户的表面诉求是什么？
- 客户真正需要的是速度、确定性、质量、资源、预算还是责任确认？
- 当前信息哪些已经确认？
- 哪些仍然未知？
- 回复以后会不会形成新的价格、范围、时间、质量或责任承诺？

推荐回复结构：

```text
确认 / 理解
→ 明确结论
→ 必要原因
→ 可执行下一步
→ 时间 / 责任边界
```

避免：

- “应该没问题”
- “我们尽量”
- “原则上可以”
- 大段客服式客套话
- 为了让客户满意而作出不可兑现承诺

---

## 3. 提案竞标 Pitch & Proposal

一个合格的 PR 提案必须同时具备：

### 前端策略深度

- 行业判断
- 用户变化
- 竞争格局
- 品牌机会
- 策略取舍
- 核心传播命题

### 后端执行颗粒度

- 阶段
- 动作
- 内容
- 媒体 / KOL
- 活动
- 负责人
- 时间
- 依赖
- KPI
- 风险
- 验收

只有漂亮概念，没有执行闭环，不算完整策略。

只有大量动作，没有为什么，也不算策略。

---

## 4. 汽车公关 Automotive PR

汽车传播最容易出现的问题之一，是 AI “记得一个差不多的参数”。

这个 Skill 设置了 **Automotive Fact Gate（汽车事实门）**。

以下信息默认属于高风险事实：

- 车型
- 配置
- 动力
- 加速
- 续航
- 补能
- 价格
- 销量
- 奖项
- 赛事成绩
- 上市地区
- “最快 / 第一 / 唯一 / 全球领先”等表述

必须优先使用目标市场对应的官方或权威资料。

禁止凭模型记忆补参数。

汽车技术传播推荐采用：

```text
技术事实
→ 使用场景
→ 用户价值
→ 可感知证明
→ 传播表达
```

而不是单纯参数堆砌。

---

## 5. 危机传播 Crisis Communications

危机发生时，AI 首先负责的是 **事实控制**，而不是抢着写声明。

必须先明确：

- 已知事实
- 未知事实
- 受影响利益相关方
- 传播范围和严重程度
- 当前业务处置动作
- 临时 Holding Line
- 唯一发言人 / 审批人
- 下次更新时间

禁止：

- 猜测事故原因
- 无证据认责或甩锅
- 发布未经核实的数据
- AI 自动向媒体发送声明
- 多个角色同时对外表达不同口径

## 6. 项目交付 Project Delivery

AI 公关员工不能只会“生产内容”，还必须能管理项目。

重要任务推荐建立 Task Contract：

```yaml
task_id:
objective:
non_objective:
inputs:
outputs:
owner:
reviewer:
start:
due:
dependencies:
risks:
acceptance_criteria:
delivery_evidence:
status:
```

每一个关键承诺都需要有：

- 负责人
- 截止时间
- 依赖条件
- 验收标准
- 变更记录

# AI 员工岗位架构

```text
PR AI Employee
│
├── PR Project Lead
│   公关项目总管
│   └─ 客户统一入口、需求判断、风险分级、任务分派
│
├── PR Strategy Director
│   公关策略总监
│   └─ 洞察、策略、叙事与传播机制
│
├── Content & Messaging Officer
│   内容与口径官
│   └─ 新闻稿、Q&A、发言稿、社媒、脚本
│
├── Project Ops
│   项目运营官
│   └─ WBS、RACI、排期、变更、交付、验收
│
└── Independent Reviewer
    独立审核官
    └─ 不参与初稿，只负责审核和阻断风险
```

推荐客户侧只看到一个统一 AI 项目入口。

专业角色在后台协作，避免多个 Agent 同时在客户群里抢答。

# 四级风险模型

| 等级 | 典型事项 | 默认动作 |
|---|---|---|
| 🟢 Green | 已确认会议时间、已批准文件、状态查询 | 白名单内可自动化 |
| 🟡 Yellow | 普通内容、策略建议、常规协调 | AI生成，真人审核 |
| 🔴 Red | 报价、合同、范围、交期、危机、媒体、高管口径、汽车参数 | 必须真人审批 |
| ⚫ Black | 跨客户泄密、泄露密钥、内部底价、绕过审批、冒充负责人 | 系统拒绝 |

# 推荐上线方式

不要一开始就把 AI 直接放到客户群自动回复。

推荐按三阶段运行：

## 第一阶段：Shadow Mode｜影子模式

```text
客户真实任务
→ AI独立判断
→ 真人正常处理
→ 对比 AI / 真人结果
→ 记录偏差
→ 更新规则和评测
```

AI 不直接对外发送。

## 第二阶段：Copilot Mode｜副驾驶模式

AI 生成完整建议，真人审核后发送。

## 第三阶段：Limited Autonomy｜有限自治

只允许低风险、明确白名单的问题自动执行。

报价、合同、危机、交期、媒体、高管口径等长期保留人工审批。

# 快速使用

让 Agent 先读取：

```text
SKILL.md
```

如果 Agent 支持按需加载，再加载对应目录：

```text
policies/
playbooks/
roles/
templates/
```

例如：

```text
客户周五问：
“这个周末能不能把系统全部部署完？”

已知条件：
专项行业内容还需要训练。

请按 PR AI Employee Skill 判断：
1. 客户真实诉求
2. 风险等级
3. 能不能直接答应
4. 建议回复
5. 是否需要人工审批
```

优秀结果不只是“帮你把话说得更客气”。

它应该识别：

> 这是一个交付时间承诺问题，因此必须先检查可行性和权限，而不是直接答应客户。

# 隐私与开源边界

这个公开仓库**不会包含**：

- 真实客户未公开资料
- 合同
- 内部报价与底价
- 私人聊天记录
- 客户群原始对话
- API Key / 密钥
- 个人隐私信息

公开版只保留经过匿名化、抽象化后可复用的方法论、规则和案例。

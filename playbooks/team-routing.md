# 公关员工协作与任务路由

先读 [SKILL](../SKILL.md) 与 [风险政策](../policies/risk-and-approval.yaml)，再查 [岗位目录](../roles/README.md)。岗位是方法与责任分工，不是已部署服务。没有多 Agent 运行时也可以按顺序加载岗位工作；要如实区分自检和独立审核。

## 选择岗位

项目总管先识别业务问题、风险与交付物。保留五个核心责任域，但小任务不必启动五个 Agent；只加载本次需要的卡片。通常从 1–3 名专才开始，复杂项目按阶段扩展。下表是可裁剪的配方，机器可读版本在 [registry.json](../roles/registry.json)。

| 配方 ID / 场景 | 主责 | 按需专才 | 主要输出 |
|---|---|---|---|
| `client-service` 客户回复/会议/新增需求 | 公关项目总管 | 项目运营官、商业提案与预算官 | 判断、答复草稿、行动/变更 |

单平台日常内容使用 `china-social.single_platform_override`：用户只指定小红书、抖音、微信、微博或B站其中一个平台时，由对应平台专才主责，仅保留所需支持岗位和独立审核责任。跨平台项目仍由社媒统筹负责；其他表中专才均为候选，不是默认全员启动。

所有配方均保留独立审核责任。`fact_check` 或汽车参数变化时先核验，再更新受影响叙事，不用增加角色人数替代证据。

## 依赖与交接

1. **入口**：记录目标、事实/假设、范围、当前授权和验收。授权明确且输入充足时直接开展内部工作，不重复索要已有批准。
2. **上游**：研究与素材盘点可并行；交付包括来源日期、市场、版本与未覆盖范围。它们支持策略取舍，不自行决定客户业务方向。
3. **生产**：策略与事实版本明确后，各平台/媒体/视觉任务可以独立生产。共用事实卡和母稿；不要在下游自行填补上游缺失参数。
4. **合稿**：项目总管处理矛盾，项目运营官追踪依赖。策略或车型事实变化后标记下游旧版本失效并重新检查。
5. **审核**：独立审核官收到原始输入、待审版本及证据。审核的 PASS 不等于发布许可；任何条件必须关闭或明确限制用途。
6. **交付**：输出版本、状态、证据与必要的审批事项。对外发送、发布、付费、部署仍按风险政策和已有授权处理，不由岗位名称决定。

交接使用 [role-handoff](../templates/role-handoff.md)。没有独立审核人员/子代理时，产出可以完成为内部草稿，状态必须为 `awaiting_independent_review`，不能靠角色切换自批。

## 状态与返工

建议状态：`draft` → `awaiting_independent_review` → `reviewed` → `awaiting_authorized_approval`（适用时）→ `approved_for_specified_use`。

审核不通过回到 `revision_needed`；证据、权限或外部依赖缺失则标 `blocked` 并说明影响范围。返工依据具体发现推进；同一缺失没有新输入时不无限重试，也不能把阻塞项当完成。实际发布/发送状态必须另外附系统回执或可核验链接。

## 制作衔接

提案按 Brief → 总策略/目录 → 逐页内容 → 图片版页面方案 → PPTX/HTML 推进。尊重用户已确认阶段；正式制作前应有文字与视觉方案确认、页数/风格/图片/讲标/PDF需求。若使用已有提案或视频技能，先确认当地可用，再交接，不把个人路径写成公共仓库依赖。没有渲染/生成工具时交付规格和提示词，并说明实际完成范围。
